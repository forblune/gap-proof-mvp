# final-audit

`design-loop` 반복이 끝난 뒤, 배포 전 마지막 게이트로 실행하는 스킬. **배포는 하지 않는다** — 배포 가능 여부만 판단해 보고한다.

## 점검 영역

1. **기능** — `tests/e2e/user-flow.spec.ts`(샘플 여정 완주, 여정 나가기→게이트 복귀), `tests/e2e/gate.spec.ts`(잘못된 코드, 샘플 우회, `?sample=1`)를 실행하고, 기존 Node 테스트(`npm test`)도 함께 확인한다.
2. **반응형** — `tests/e2e/responsive.spec.ts`로 390/768/1024/1440에서 가로 오버플로가 없는지 확인한다.
3. **브라우저** — `npx playwright test`를 chromium/firefox/webkit 세 프로젝트 모두에서 실행하고 브라우저별 결과를 따로 표에 기록한다.
4. **접근성** — `tests/e2e/accessibility.spec.ts`(axe-core, wcag2a/wcag2aa)로 `serious`/`critical` 위반이 있는지 확인한다. 위반이 남아 있다면 배포 가능 여부 판단에 직접 반영한다(차단 사유로 취급).
5. **성능** — `lighthouse`로 `/`, `/demo`(게이트 상태) 성능·접근성·SEO 점수를 측정한다(로컬 dev 서버가 아니라 `npm run build && npm start`로 띄운 프로덕션 빌드 기준을 우선한다).
6. **문체와 콘텐츠** — `professor-review`를 다시 실행해 7개 항목 점수를 최신 상태로 갱신하고, 이전 사이클 대비 남은 저점 항목을 표시한다.

## 절차

1. 위 6개 영역을 순서대로 실행한다. 각 영역은 실패해도 다음 영역 점검을 계속 진행한다(전체 그림을 먼저 파악한 뒤 판단하기 위함).
2. 실패·경고를 숨기지 않는다. 재현 안 되는 flake로 의심되면 1회 재실행해 확인하고, 재현되면 그대로 기록한다.
3. 미해결 문제를 심각도(배포 차단/권고/사소)로 분류한다.
   - **배포 차단**: 기능 회귀, 5xx/네트워크 실패, `serious`/`critical` 접근성 위반, 브라우저 중 하나에서라도 핵심 플로우 실패.
   - **권고**: 반응형 미세 오버플로, 성능 점수 저하, 문체·콘텐츠 저점 항목.
   - **사소**: 스타일 디테일, 향후 개선 아이디어.
4. 배포 가능 여부를 명시적으로 한 문장으로 결론짓는다 ("배포 가능" / "배포 차단 — 이유").

## 주의사항

- 이 스킬은 실제 배포(프로덕션 도메인 발행, `wrangler deploy` 등)를 **절대 실행하지 않는다.** 배포 여부는 사람이 결정한다.
- 기존 Node 테스트나 기존 기능을 손상시키는 변경은 이 스킬 범위 밖이다 — 발견하면 보고만 하고 수정은 `design-loop`로 넘긴다.
