# design-loop

`professor-review`가 찾은 문제를 실제로 고치는 반복(iteration) 스킬. 한 번에 너무 많이 바꾸면 무엇이 효과가 있었는지 알 수 없으므로 **한 사이클당 최대 3개** 문제만 다룬다.

## 절차 (한 사이클)

1. **문제 선정** — `professor-review` 결과(또는 이번 스킬 실행 직전에 새로 실행한 결과)에서 점수를 가장 많이 깎는 항목 최대 3개를 고른다. 선정 기준:
   - 여러 화면·여러 뷰포트에 걸쳐 반복되는 문제를 우선한다(국소적 1회성 문제보다 우선순위 높음).
   - 접근성 `serious`/`critical` 위반은 점수와 무관하게 항상 후보에 포함한다.
   - 3개를 넘는 후보가 있으면 나머지는 다음 사이클로 미루고, 이번 사이클에서 다루지 않는 항목을 명시적으로 기록한다.
2. **수정** — 선정된 문제만 최소한으로 고친다. 디자인 토큰·기존 컴포넌트 패턴을 재사용하고 새 추상화를 만들지 않는다.
3. **검증 파이프라인을 순서대로, 하나라도 실패하면 다음 단계로 넘어가지 않고 그 자리에서 원인을 고친다.**
   1. `npm run build`
   2. `npm run lint`
   3. 기존 Node 테스트: `npm test`
   4. `npx playwright test` (tests/e2e — 홈·게이트·사용자 흐름·반응형·콘솔·네트워크·스크린샷)
   5. 접근성: `npx playwright test tests/e2e/accessibility.spec.ts`
4. **재평가** — `professor-review`를 다시 실행해 선정했던 3개 항목의 점수 변화를 확인한다. 스크린샷 diff(`--update-snapshots` 전후)로 의도한 변경만 반영됐는지 확인한다.
5. 사이클 결과를 기록하고 다음 사이클로 넘어갈지(남은 문제 존재) 여기서 멈출지(모두 해결 또는 사용자 확인 필요) 보고한다.

## 출력 형식

```
## design-loop 사이클 N

### 이번 사이클에서 다룬 문제 (최대 3개)
1. [항목] 문제 설명 — 수정 내용 (파일:라인)
2. ...
3. ...

### 다루지 않고 다음으로 미룬 문제
- ...

### 검증 결과
- build: pass/fail
- lint: pass/fail
- npm test: N/N pass
- playwright: N/N pass (브라우저별)
- 접근성: serious/critical 위반 수 (이전 → 이후)

### 재평가 점수 변화
| 항목 | 이전 | 이후 |
|---|---|---|
```

## 주의사항

- 프로덕션 배포 명령(`vinext start` 이후 배포 파이프라인, 도메인 발행 등)은 절대 실행하지 않는다.
- 검증 파이프라인 실패를 숨기거나 `--no-verify`, 테스트 스킵으로 우회하지 않는다. 실패하면 원인을 고치거나 사이클을 중단하고 보고한다.
- 스크린샷 베이스라인을 갱신할 때는 의도한 디자인 변경으로 인한 diff인지 반드시 확인한 뒤에만 `--update-snapshots`를 실행한다.
