## 3. 점수 근거 — 무엇이 왜 올랐는가 (기준선 57.4 → 최종 73.5, +16.1점)

이번 최종 감사에서 프로덕션 빌드(`npm run build && npm start`)를 직접 띄우고 Playwright chromium으로 라이트/다크 × 1440px(모바일 드로어만 390px) 스크린샷을 재촬영해 아래 강점을 재확인했다(`docs/quality-loop/screenshots/final/{light,dark}/`).

- **다크 네이비 히어로 + 최종 CTA 북엔드 구조** (`home.png`, 라이트·다크 공통): 홈페이지 첫 화면과 마지막 CTA 섹션만 다크 네이비 배경을 쓰고 중간 섹션은 크림/오프화이트/탄톤이 교대하는 하이브리드 구조 — Loop 1, 6에서 도입된 챕터별 배경 그룹화(01~08 자동 번호)가 그대로 유지·재확인됨.
- **STEP4 결과 화면의 2단 카드 구성** (`demo-result.png`): 개인용 GapProof 증거카드(목표 직무·확인된 역량·대표 근거 인용·이번 주 다음 행동)와 상담사용 Gap Brief(상담 목표·현재 강점·우선 격차·다음 상담 질문·기관 공유 범위)가 나란히 배치되어 완성도 높게 렌더링됨 — Loop 9·10에서 확립된 패턴이 이번 감사에서도 회귀 없이 동일하게 동작.
- **`/technology` 커스텀 SVG 기술 로고 5종 + 보안/검증/제한사항 섹션** (`technology.png`): 아이콘 없는 텍스트 벽이었던 기준선 대비 Loop 2·9에서 도입된 시각 자산이 라이트·다크 모두 고품질로 유지됨.
- **모바일 드로어 메뉴** (`mobile-drawer.png`, 390px): 햄버거 메뉴로 전체 내비게이션(6개 링크)과 테마 토글, 데모 CTA가 오버레이 형태로 정상 노출되며 라이트·다크 대비 모두 양호.
- **기능·회귀 없음**: `npm test` 37/37, `npx playwright test` 114/114(3브라우저), axe-core serious/critical 위반 0건(33케이스) — Loop 1부터 12까지 축적된 접근성·반응형 개선이 한 번도 퇴행하지 않고 유지됨.

이 강점들이 기준선(57.4) 대비 총점을 16.1점 끌어올린 핵심 근거이며, 특히 "정보 구조"(6.7→7.5), "실제 서비스 완성도"(6.7→7.5), "아이콘·이미지·시각 자산"(1.3→7)의 상승 폭이 가장 크다 — 기준선 조사에서 "아이콘·이미지·시각 자산 활용"이 1.3/10으로 압도적 최저점이었던 것이 이번 최종 상태에서는 7/10까지 개선됨.

## 5. 자동평가(에이전트 기반 독립 리뷰)의 한계

이번 프로젝트의 점수 이력 자체가 이 한계를 실증한다: **Loop 10 종료 시점에서 코드를 전혀 바꾸지 않은 채 다른 리뷰어 에이전트가 재평가했을 때 총점이 77.6 → 73.5로 4.1점 떨어졌다.** 이는 실제 품질이 후퇴해서가 아니라(같은 커밋 `f9735a0`), 리뷰어 에이전트마다 스크린샷을 보는 관점·감점 기준 적용 강도·"권장"과 "결함"을 구분하는 기준이 달랐기 때문이다. 이 사실 하나만으로도 아래 한계들이 추상적 우려가 아니라 이 프로젝트에서 실제로 관측된 현상임을 알 수 있다.

- **리뷰어 에이전트 간 채점 변동성**: 위에서 확인한 77.6→73.5(코드 변경 없음)처럼, 동일 산출물도 어떤 에이전트 인스턴스가 채점하느냐에 따라 총점이 4점 이상 흔들릴 수 있다. design-loop-11/12에서도 같은 73.5 기준선에 대해 서로 다른(그러나 유사한) 변경이 매번 76점으로 재평가됐는데, 이 "76"이라는 숫자 자체도 재현 가능한 절대값이라기보다 해당 순간 그 리뷰어가 내린 상대적 판단에 가깝다.
- **스크린샷 기반 판단의 한계**: 이 감사와 앞선 모든 professor-review는 Playwright로 촬영한 정지 스크린샷과 computed style 실측에 의존한다. 실제 사용자가 스크롤하며 느끼는 리듬감, 클릭 후 전환 애니메이션, 로딩 중 상태 등 "정지 이미지로 환원되지 않는" 경험 요소는 반영되지 않는다(예: Loop 6에서 "배경 전환 0회 해소"를 시각적으로는 달성했지만 재검토 스스로 "지각 임계값에 근접해 체감 개선은 약함"이라고 기록한 사례).
- **실제 인간 교수의 주관적 판단·강의 맥락 미반영**: 이 점수는 교수님이 실제 수업에서 무엇을 강조했는지, 발표 당일의 구두 설명·질의응답 대응, 팀의 노력이나 성장 서사에 대한 정성적 평가, 다른 팀 프로젝트와의 상대적 비교 등을 전혀 알지 못한 상태에서 산출됐다. `PROFESSOR_REVIEW_BASELINE.md`가 참조한 "교수님 원본 피드백"도 텍스트로 전달된 요약일 뿐, 실제 톤·강조점·암묵적 기준을 완전히 담아내지 못했을 가능성이 있다.
- **채점 기준 자체의 재해석 여지**: "권장"과 "결함"의 경계(예: 980px 콘텐츠 폭), "정보 손실 없는 축약"과 "핵심 가치제안 은폐"의 경계(예: STEP2 details 접기) 같은 항목은 이번 리뷰들에서도 `requiresHumanJudgment`로 명시적으로 분류됐다 — 즉 리뷰어 스스로도 "이 감점이 객관적으로 옳다"고 주장하지 않았다.
- **기준선 수치 자체의 미세한 불일치**: 이 문서 작성을 지시한 오케스트레이터가 전달한 기준선(57.3)과 `PROFESSOR_REVIEW_BASELINE.md`에 실제 기록된 값(57.4)이 0.1점 어긋나 있었다 — 사소하지만, 여러 단계·여러 에이전트를 거치며 숫자가 완벽하게 보존되지 않을 수 있음을 보여주는 방증이다.

### "이 점수가 실제 교수님 점수와 동일하다고 주장할 수 없는 이유"

이 73.5점은 실제 지도교수가 채점한 점수가 아니라, "교수님이 준 서면 피드백 요지"를 참고 자료로 삼아 AI 리뷰어 에이전트가 스크린샷·DOM·접근성 도구 실측치만으로 재구성한 **대리 평가(proxy evaluation)**에 불과하다. 위에서 실증했듯 동일한 코드베이스도 리뷰어 인스턴스에 따라 4점 이상 흔들렸고, 스크린샷에는 담기지 않는 발표 태도·구두 설명·강의 맥락·다른 팀과의 상대 비교·교수님 개인의 암묵적 취향과 우선순위가 실제 성적에는 반영되기 마련이므로, 이 점수는 "지금 상태가 대략 어느 방향으로 개선되고 있는지"를 가늠하는 내부 지표로만 사용해야 하며 실제 학점·평가 결과를 예측하거나 대체하는 근거로 사용해서는 안 된다.
